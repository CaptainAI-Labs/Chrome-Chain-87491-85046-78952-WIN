利用链路研究 · 从「能打通」到 43%

打通≠稳定。真正的工程量在概率结构：stage1 需要恰好等到一次 young GC（必须 fresh renderer，脏堆重载只有 ~3%），78952 竞态有固有窗口。方法是把漏损逐段归因、逐段消灭。

根因 · 并集 kind 对「写」不再是安全近似

内联 sort 对多态反馈 {PACKED_SMI, PACKED} 求 elements-kind 并集（= PACKED）并按它特化「排序快照写回」。并集对只读迭代（forEach/map）是安全上界；但 sort 多了写回——回调里 fill(0) 把数组原地窄化回 PACKED_SMI 后，回调后的 CheckMaps 只检查 map ∈ 原集合、照过，写回仍按 PACKED 语义把 HeapObject 指针塞进声称全是 Smi 的数组，且跳过写屏障。

// 编译图结构（修复前） checkReceiverMaps(); temp = copy(receiver.elements); // 按并集 kind 快照 insertionSort(temp, comparefn); // 纯 JS，可任意副作用 checkReceiverMapsAndLength(); // 窄化后的 map 照过 copy(temp, receiver.elements); // 按 PACKED 写回 → 指针入 Smi 数组
利用 · 年轻代 GC 一瞬的窗口

写屏障被跳过意味着 GC 不知道旧生代对象引用了新空间：GC 移动对象后旧指针仍滞留新空间。在旧指针位置喷射假 JSArray 头（map=PACKED_DOUBLE），template.slice() 把回收内存当 double 数组复用——得到与 victim 数组共享 elements 的 cage 内任意读写（read32/write32）。

错误本质① handler 无条件信任客户端声明的 extra_memory_ranges ② ReadUpTo 重试长度不钳位回 size
信任边界划错了地方

崩溃报告由非沙箱的 crashpad-handler 收集。客户端 PE 节 "CPADinfo"（CrashpadInfo）里的 extra_memory_ranges 指针告诉 handler 崩溃时额外读取哪些区间——渲染器内的攻击者可完全控制这份声明，而 handler 照单全收。

三拍时序（放大图见 §06）
// BEAT 1 微脉冲：6 个内核线程翻转目标页保护 PAGE_NOACCESS ↔ PAGE_READWRITE // 微脉冲窗口 // BEAT 2 ReadUpTo 无钳位重试 请求 size = 0xB8（触发段精确设定） 首读撞 NOACCESS → 重试读出 0x168 → 溢出 0xB0 盖到相邻堆槽 → 相邻对象 = minidump 流的 SMMW（StreamMinMaxWriter） // BEAT 3 模板劫持 → 派发 SMMW 模板被改 → Next() 把 victim 页 memcpy 进 handler .data（plant 区） plant 区：[Q]=宽字符 DLL 名 · [Q+8]=LoadLibraryW Flush() 尾部 CFG 派发 LoadLibraryW(Q) → handler 内任意 DLL 加载
